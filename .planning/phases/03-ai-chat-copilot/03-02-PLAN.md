<objective>
Make the conversation survive a refresh and stop the prompt growing without bound: add the
read/write half of `chat_messages` the module's own docstring reserved for this phase, wire
it into `POST /api/chat`, expose `GET /api/chat`, and cap how much history reaches the model.

Purpose: Plan 03-01 proved the round trip but threw the conversation away. Without
persistence the panel resets on every reload, which is the single most visible way a chat
assistant feels broken. Capping the prompt context is decided here rather than left
implicit (03-RESEARCH.md Pitfall 5 / A2 — no policy exists in PLAN.md for this table).

Output: `insert_message()` / `get_messages()`, `GET /api/chat`, persistence inside
`POST /api/chat`, a `PROMPT_HISTORY_LIMIT` cap, and determinism tests for the mock branch.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `chat_messages.actions` (stored JSON) → route deserialization | Previously-written data re-enters the request path and is re-validated |
| stored history → LLM prompt | Prior user-authored text is replayed into the model on every subsequent request |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-07 | Tampering | `_actions_from_json()` in `app/routes/chat.py` | medium | mitigate | A NULL, empty, malformed, or shape-invalid `actions` value degrades that one message to empty action lists inside a `try / except (json.JSONDecodeError, ValidationError, TypeError, KeyError)` — a single bad row cannot 500 the whole history endpoint or block the panel from hydrating. |
| T-03-08 | Denial of Service | LLM prompt assembly | medium | mitigate | `PROMPT_HISTORY_LIMIT = 20` is applied inside `build_messages()` so no call site can bypass it; `get_messages()` defaults to a 50-row limit. Per-request prompt size is bounded regardless of how many rows accumulate over a session (03-RESEARCH.md Pitfall 5). |
| T-03-09 | Tampering | replayed history in the prompt | medium | mitigate | Stored history is replayed as `{"role", "content"}` message dicts only; the `actions` column is never folded into prompt text, so a prior turn cannot re-assert an execution outcome to the model. Any action the model proposes in response still passes Plan 03-01's `_validate_trade_item()` gate and `execute_trade()`'s own guard before touching state. |
| T-03-10 | Information Disclosure | SQLite writes of chat content | low | accept | Chat content is stored in plaintext in `db/finally.db`. Accepted: single-user local demo with no auth boundary and no second party to protect against; the same file already stores the full trade history in plaintext. |

## Canon referrals (not minted as bespoke prohibitions)

- SQL injection through message content is canon — every statement in `app/db/chat_messages.py` is parameterized, same as every other module in `app/db/`; covered by `/gsd-secure-phase`.
- Data-retention / right-to-erasure for stored conversation content is canon (GDPR-class) — breadcrumb to `/gsd-secure-phase`; not minted here, and out of scope for a single-user local demo.
</threat_model>

<planner_assumptions>
1. **Prompt-context cap = 20 messages; `GET /api/chat` limit = 50 (03-RESEARCH.md A2).**
   PLAN.md specifies no pruning policy for `chat_messages` and, unlike
   `portfolio_snapshots`, does not declare unbounded growth an accepted tradeoff. Decided
   here rather than left implicit: rows are never deleted (matching the project's existing
   posture for `trades` and `portfolio_snapshots`), but the prompt reads at most the last
   20 and the panel at most the last 50. Both are single constants, trivially changed.
2. **`rowid` rather than `created_at` for history ordering.** Two rows written within one
   request can carry identical ISO timestamps, which would make ordering arbitrary exactly
   where user-then-assistant order matters most. `rowid` is monotonic per insert and needs
   no schema change. If a later phase ever converts the table to `WITHOUT ROWID`, this
   ordering breaks — noted for whoever does that.
</planner_assumptions>
