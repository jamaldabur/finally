right.

and given its mirror-image sibling here), PORT-04 (sell rejected on insufficient shares).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → `POST /api/portfolio/trade` | Untrusted `ticker` / `side` / `quantity` cross here, now on the sell path as well as the buy path |
| Service → SQLite (`db/finally.db`) | A sell deletes rows; the delete predicate is caller-influenced (`ticker`) |
| Two concurrent requests → shared `cash_balance` | Overlapping read-modify-write of the same mutable state |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-01 | Tampering | `DELETE FROM positions` in `app/db/positions.py` | high | mitigate | `?` placeholders with a params tuple for both `user_id` and `ticker`, matching `app/db/watchlist.py`; no string interpolation of the ticker into the delete predicate |

| T-01-03 | Tampering / Repudiation | Negative or zero sell quantity | medium | mitigate | `quantity: float = Field(gt=0)` on `TradeRequest` rejects at the FastAPI layer (422); the service additionally never reaches a write when the share check fails |
| T-01-04 | Tampering | Unrecognized ticker reaching `positions` / `trades` on the sell path | high | mitigate | `execute_trade()` normalizes and gates on `await market_source.is_valid_ticker(ticker)` before either branch runs — the same single gate covers buy and sell |
| T-01-05 | Tampering (data integrity) | Float residue leaving a phantom near-zero position | medium | mitigate | `abs(new_quantity) < QUANTITY_EPSILON` deletes the row; the sell-sufficiency check adds the epsilon to the held side so a legitimate sell-all is never spuriously rejected; no `int()` cast anywhere in the path |
