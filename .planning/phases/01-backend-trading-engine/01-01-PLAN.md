## Locked API contract (decided here; RESEARCH.md Open Question 2 delegates this to the planner)

Phase 2 (frontend) and Phase 3 (chat) consume this contract directly. It is locked now so no later
plan re-litigates field names.

**`POST /api/portfolio/trade`** — request body
- `ticker: str` (`min_length=1`), `side: Literal["buy", "sell"]`, `quantity: float = Field(gt=0)`

**`POST /api/portfolio/trade`** — 200 response
- `trade`: `{id, ticker, side, quantity, price, executed_at}`
- `cash_balance`: float — the post-trade balance
- `position`: `{ticker, quantity, avg_cost}` or `null` when a sell fully closes the position

**Rejections** — HTTP 400 with FastAPI's standard `{"detail": "<reason>"}`. Locked message prefixes,
so tests assert on a stable prefix rather than full prose:
- `Insufficient cash: ` …
- `Insufficient shares: ` …
- `No live price available for ` … (Plan 01 introduces this; see locked decision below)
- `Unknown ticker: ` …

Pydantic-level violations (`quantity <= 0`, bad `side`) surface as FastAPI's own 422, not 400.

## Locked behavioural decision (RESEARCH.md Open Question 1 / Assumption A1)

A trade for a ticker that is in `TICKER_UNIVERSE` but has no entry in `PriceCache` (i.e. not on the
watchlist, so `run_update_loop` has never priced it) is **rejected with 400**, never silently
auto-added to the watchlist. Market orders fill at an observed price or they do not fill.
Rationale: matches the "market orders only, no magic side effects" spirit of `planning/PLAN.md` §6/§8.
