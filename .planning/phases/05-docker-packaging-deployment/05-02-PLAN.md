<objective>
**As a** user of FinAlly, **I want to** start and stop the whole application with one command on my
own operating system, **so that** I never have to remember a `docker run` incantation — and so that
running the command twice by mistake costs me nothing.

Plan 05-01 proved the image works. This plan wraps it in the four scripts PLAN.md §11 names, and
makes re-running any of them safe.

Purpose: DEPLOY-03 is the requirement that turns "there is a Docker image" into "there is a product a
course student can launch." Idempotency is the whole point: a student who is unsure whether the app
is running must be able to type the start command again and get a clear answer instead of a container
name collision, and must be able to type stop twice without wondering whether the second one ate
their portfolio.

Output: `scripts/start_mac.sh`, `scripts/stop_mac.sh`, `scripts/start_windows.ps1` and
`scripts/stop_windows.ps1`, each validated structurally and — for the PowerShell pair, which is
native to this development machine — through a real start / re-start / stop / re-stop round trip
against the running daemon.
</objective>

    1. **Argument validation, before anything else.** Accept zero arguments, or exactly the single

       does not appear to be running and that Docker Desktop (or the daemon) must be started, then
       exit 1. Discard the command's own output; only its exit status matters.
    4. **Already-running check (D-07).** Query the daemon with an anchored name filter and a running
       status filter — `docker ps --filter "name=^${CONTAINER_NAME}$" --filter "status=running" -q` —
       and treat a non-empty result as "already up". The anchors are load-bearing: an unanchored
       filter matches any container whose name merely contains the word. When it is already up AND
       the rebuild flag was not passed, print that FinAlly is already running at `$APP_URL` and exit
       0. Do not restart it, do not error.

       **P-02 (planner decision):** when it is already up AND the rebuild flag WAS passed, the
       rebuild wins — print that an explicit rebuild was requested, remove the running container,
       and continue through the build and run steps. D-06 and D-07 each describe one half of this
       situation and neither resolves the overlap; without this rule the rebuild flag would be
       silently ignored exactly when a user reaches for it.
    5. **Clear any stopped container of the same name.** A previously stopped container still holds
       the name and would make `docker run --name` fail with a collision. Query `docker ps -a` with
       the same anchored name filter and, if anything comes back, remove it. This is what makes a
       stop-then-start cycle work, and it is safe because the container holds no state — every byte
       the user cares about is on the bind mount.
    6. **Build if needed (D-06).** Build when the rebuild flag was passed, or when
       `docker image inspect "$IMAGE_TAG"` does not succeed. Build with
       `docker build -t "$IMAGE_TAG" "$REPO_ROOT"` so the context is the repository root regardless of
       where the script was invoked from. Print a line before the build saying it may take several
       minutes on a first run, because it will.
    7. **Resolve and create the mount source (D-02).** `DB_DIR="$REPO_ROOT/db"`, then `mkdir -p
       "$DB_DIR"`. Creating before mounting matters: Docker would otherwise create the path itself
       with daemon-owned permissions.
    8. **Run.** `docker run -d --name "$CONTAINER_NAME" -p "${HOST_PORT}:8000" --env-file
       "$REPO_ROOT/.env" -v "$DB_DIR:/app/db" "$IMAGE_TAG"`, with every expansion quoted. Send the
       printed container id to /dev/null; the user does not need it.
    9. **Wait for readiness.** Poll `GET $APP_URL/api/health` in a bounded loop — roughly forty
       attempts one second apart — and stop as soon as it succeeds. If the loop exhausts, print that
       the container started but never became healthy, tell the user to run `docker logs
       $CONTAINER_NAME`, and exit 1. Do not print a success URL for a container that is not
       answering.
    10. **Print the URL**, then **best-effort browser open (D-08)**. Use `open` when that command
        exists, otherwise `xdg-open` when that exists, otherwise do nothing. The whole attempt must
        be unable to fail the script: under `set -e` that means suppressing errors and forcing
        success on that line. A headless machine, a CI runner, or a missing opener must leave a
        successful start successful.

    1. Accept zero arguments; anything else prints usage to stderr and exits 1.
    2. If `docker info` does not succeed, print that FinAlly is not running (the daemon being down
       means it definitionally is not) and exit 0. This keeps stop idempotent in the one case where
       an error would be least useful — a user shutting down who already quit Docker Desktop.
    3. Query the same anchored running filter. When nothing comes back, print "FinAlly is not
       running." and exit 0 (D-07).
    4. Otherwise `docker stop "$CONTAINER_NAME"`, then print that FinAlly is stopped and that the
       data in `db/` has been left untouched.

    Create both PowerShell scripts under `scripts/`. Each begins with `$ErrorActionPreference =

    **Argument validation is declarative here, not hand-rolled.** `start_windows.ps1` declares
    `param([switch]$Build)` as its first statement. PowerShell then rejects any unrecognised
    parameter with a non-zero exit on its own, which is both safer and shorter than parsing

    invocation. `stop_windows.ps1` declares an empty `param()` for the same reason.

    Shared constants, matching Task 1 exactly: `$ImageTag = "finally:latest"`, `$ContainerName =

    Resolve the repository root from the script's own location: `$RepoRoot = (Resolve-Path (Join-Path

    working directory, which is the whole point (D-02).

    **`start_windows.ps1`** follows Task 1's step order exactly:

    1. `param([switch]$Build)` — argument handling, first statement in the file.
    2. `.env` guard (D-09): `Test-Path` the project-root file; when absent, write an error naming

       never `Get-Content` that file.
    3. Daemon reachability: run `docker info`, discard its output, and `exit 1` with a clear message
       when it did not succeed. Check `$LASTEXITCODE` after the call; a native command's failure does
       not raise a PowerShell exception even under `$ErrorActionPreference = "Stop"`, so an
       exit-code check is required rather than a try/catch.
    4. Already-running check (D-07): `docker ps --filter "name=^$ContainerName$" --filter
       "status=running" -q`, non-empty result means up. Note that `$ContainerName$` inside a
       double-quoted PowerShell string interpolates the variable and leaves the trailing `$` as a
       literal anchor — confirm the composed filter string is what you intend before relying on it.

       `-Build` WAS passed, apply P-02 from Task 1: say an explicit rebuild was requested, remove
       the running container, and continue.

       then `$DbDir = (Resolve-Path $DbDir).Path`. Resolving before creating throws on a fresh
       clone where `db/` has not yet been made.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user command line → script → `docker` CLI | Arguments supplied by the user reach a process-spawning tool; unvalidated input must not cross |
| script → project `.env` | The scripts stand next to a file containing a live API key; anything they print goes to a terminal and possibly a CI log |
| script → host `db/` directory | The scripts decide which host directory becomes the container's writable database path, and whether a stop is destructive |
| script → Docker daemon state | The scripts' entire notion of "is it running" comes from the daemon; a sloppy query is a wrong answer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08 | Tampering | Script argument handling | medium | mitigate | Arguments are parsed before any daemon call: bash uses an exact-equality `case` arm for the single accepted flag and exits 1 with usage on anything else; PowerShell uses `param([switch]$Build)` so the shell itself rejects unknown parameters. No user-supplied string is ever interpolated into a `docker` invocation. Verified by an unknown-flag rejection run (Task 1) and a declarative-parameter grep (Task 2) |
| T-05-09 | Information Disclosure | `.env` handling in scripts | medium | mitigate | The scripts test only for file existence and hand the path to `--env-file`; a negative grep in both tasks rejects any instruction that reads the file's contents, so no key reaches stdout or a CI log |
| T-05-10 | Tampering / data destruction | Stop scripts | high | mitigate | Neither stop script contains a removal, prune, move, or truncate instruction — enforced by negative greps over comment-filtered source in both tasks — and both tasks assert `db/finally.db` still exists after the stop sequence. PLAN.md §11 and D-08 both require stopping to leave data alone |
| T-05-11 | Tampering | Bind-mount source resolution | medium | mitigate | The mount source is built from `dirname "$0"` / `$PSScriptRoot`, created before use, and quoted on expansion (D-02); both tasks additionally invoke a script from an unrelated working directory to prove the resolution does not depend on the caller (RESEARCH Pitfall 2) |
| T-05-12 | Spoofing | Container identity detection | low | mitigate | Detection uses `docker ps --filter "name=^finally$" --filter "status=running" -q` against the daemon's own state; the regex anchors prevent an unrelated container whose name merely contains the word from being mistaken for FinAlly, and no host-side lock or PID file is kept that could drift |
| T-05-13 | Elevation of Privilege | Script execution policy on Windows | low | accept | The verification runs PowerShell with `-ExecutionPolicy Bypass` because the scripts are unsigned local files. | T-05-SC | Tampering | npm / pip / cargo installs | high | mitigate | This plan introduces no packages at all — it only invokes `docker build` against the Dockerfile Plan 05-01 already audited.
