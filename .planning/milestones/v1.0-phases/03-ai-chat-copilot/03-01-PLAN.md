<objective>
Prove the whole agentic chat loop end-to-end on one path: a user message goes to the LLM
(mock or real), comes back as validated structured output, and a trade it requested is
executed through the same `execute_trade()` the trade bar uses — with each action's real
outcome annotated and returned.

Purpose: this is the architectural risk of Phase 3 concentrated into one slice. If
LLM-proposed actions cannot flow through the existing validated path and come back
annotated, every later chat feature is built on sand. Proving it first, on the agent's
best early-context tokens, catches that after one commit instead of after ten.

Output: `backend/app/llm/` (schema, client, mock, actions), `POST /api/chat`, the
`execute_trade()` validation guard that makes the shared path safe for an untrusted
caller, and route tests that exercise the full round trip.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/chat` | Untrusted free-text user input enters the server and reaches a model that can trigger state changes |
| server → OpenRouter (`openrouter.ai`) | Outbound call carrying the user's portfolio context and authenticated by `OPENROUTER_API_KEY` |
| LLM response → action execution | Untrusted model output crosses into cash-balance and position mutation |
| package registry → `backend/uv.lock` | Third-party code enters the runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `app/llm/actions.py` → `execute_trade()` | high | mitigate | Two independent layers: `_validate_trade_item()` rejects non-finite / non-positive quantity and any side outside {buy, sell} before `execute_trade()` is called (Task 2), and the guard added at the top of `execute_trade()` itself rejects the same for every caller (Task 3). Regression tests assert no state change on rejection. |
| T-03-02 | Elevation of Privilege | `app/llm/actions.py` | high | mitigate | Chat actions are applied only by calling the existing `execute_trade()` / `add_watchlist_ticker()` / `remove_watchlist_ticker()` — verified by a negative grep asserting `actions.py` never reaches cash-balance, position-upsert, or trade-insert persistence directly. Exactly one validate-and-apply path exists (PLAN.md §9 step 6). |
| T-03-03 | Information Disclosure | `app/llm/client.py` logging | high | mitigate | The exception handler logs the exception type and message only — never the request body, the response body, or an environment-variable value. Mirrors the `MASSIVE_API_KEY` handling convention in `app/market/massive.py`. The system prompt embeds no secret; only the LiteLLM transport reads the key. |
| T-03-04 | Spoofing | assistant `message` text | medium | mitigate | A prompt-injected message cannot forge an outcome: the model's `message` is generated before execution and outcomes are computed by the server from the real `TradeResult`. The system prompt forbids the model asserting success or failure, and the response contract carries outcomes as separate structured fields the frontend reads instead of parsing prose. |
| T-03-05 | Denial of Service | `POST /api/chat` LLM call | medium | mitigate | Every failure mode of the outbound call (network error, rate limit, missing key, malformed body, empty content) degrades to a 200 message-only response through `parse_llm_response`'s fallback and the broad exception handler — a failing provider cannot 5xx or hang the endpoint's contract. |
| T-03-06 | Repudiation | chat-originated trades in `trades` | low | accept | The `trades` table does not record origin, so a chat-originated fill is indistinguishable from a trade-bar fill.
