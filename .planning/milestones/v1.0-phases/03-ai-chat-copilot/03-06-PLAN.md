<objective>
Close G-03-3, a blocker: make the chat client robust to the free router's documented output
quirks so a correctly-formed model response can never lose its trades, and so raw model text
can never reach the user as the assistant's reply.

Purpose: the UAT report looked cosmetic — a leaked instruction string shown as a chat
message — but the debug session reproduced the same branch silently dropping a real,
correctly-requested trade when the model wraps its JSON in a markdown code fence. That is a
failure of this project's core value, the agentic execute step, not a display bug. The
project's own `agent-teams` branch hit this exact class of free-router flakiness and built
fence-stripping, a fallback model and a constant fallback message for it; none of that was
carried over when Plan 03-01's user-approved deviation adopted the same model.

Output: a `client.py` whose parse path recovers fenced JSON before giving up and returns a
fixed message when it cannot, whose structured call no longer streams (which is what made
the error path silent), and which fails over exactly once on a transient provider error —
plus tests whose oracles assert message content instead of truthiness.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output → `parse_llm_response()` | Untrusted text from a rotating pool of free backing models is parsed and, on success, becomes executable trade instructions |
| model output → fence-stripping regex | Untrusted text drives a pattern match whose result is re-parsed |
| provider exception → failover decision | An exception raised by a remote service decides whether a second paid-for-in-quota request is issued |
| fallback attempt → prompt contents | A second model is asked to answer after a first attempt failed; what it is told is a security-relevant choice |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-25 | Denial of Service | failover path in `client.py` | medium | mitigate | Exactly two sequential attempts per turn — one primary, one fallback — expressed as two straight-line calls with no loop, recursion or counter. Negative greps assert no loop construct and no library-level retry multiplier exist in the module, and a test asserts the completion function is called at most twice in any failure combination. A retry storm against an already rate-limit-prone shared free pool is the realistic failure mode here, and it is bounded structurally rather than by a limit constant. |
| T-03-26 | Denial of Service | `_strip_code_fence()` regex on untrusted text | medium | mitigate | The pattern is anchored at both ends, compiled once at module scope, and applied exactly once per parse — never in a loop and never re-applied to its own output. The retry only runs when the stripped text actually differs from the input, so a text that strips to itself terminates immediately. |
| T-03-27 | Elevation of Privilege | prompt contents of the fallback attempt | medium | mitigate | The fallback is handed the same message list object the primary received. Nothing derived from the failed response is injected into it, so a hostile or manipulated first response cannot shape what the second model is asked, and the fallback answers the user's original message with the user's original portfolio context. A test asserts the two calls receive equal message lists. |
| T-03-28 | Spoofing | fence-recovered `trades[]` becoming executable instructions | high | mitigate | Fence recovery only ever re-runs the same `ChatResponseSchema` validation against the stripped text — it never hand-parses, never repairs malformed JSON, and never synthesises an action. Recovered items therefore reach `app/llm/actions.py` through the identical validation and execution path as a normally-parsed response, where per-item validation and `execute_trade()`'s own guards still apply. Recovery restores a dropped-but-legitimate request; it does not create a second, weaker route into trade execution. |
| T-03-29 | Information Disclosure | warning log on parse failure and on failover | low | mitigate | Logging is limited to exception type, exception message, the model names, and a bounded prefix of the raw text — never the full response body, never the message list (which carries the user's cash balance and positions), and never an environment variable value.
