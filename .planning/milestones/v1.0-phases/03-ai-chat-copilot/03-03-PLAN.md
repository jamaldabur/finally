<objective>
Put the chat loop in front of the user: a third column on the terminal where they type a
message, watch it go, and read the assistant's reply — with the prior conversation already
there when the page loads.

Purpose: Plans 03-01 and 03-02 built a working endpoint that nobody can reach. This plan
completes the vertical slice to the browser, which is where the phase's goal actually lands
("a user can converse with an AI assistant"). It also closes the loop back to the rest of
the terminal: a trade the assistant executes must show up in the header and the positions
table immediately, not after a reload.

Output: chat wire types, the two `lib/api.ts` access points, `chatStore.tsx`, the panel
shell with its input and message list, and the third column in `app/page.tsx`.

Note on wave ordering: this plan runs in the same wave as Plan 03-02, which lands
`GET /api/chat`. That is deliberate and safe — the two plans share no files, and every
automated check here (typecheck, lint, static export build, source greps) passes without a
live backend. The live end-to-end confirmation is Plan 03-04's job, which depends on both.
</objective>

      input knows whether to clear itself.
    - `watchlistRevision: number` — incremented on every send whose response contains at
      least one `watchlist_changes` item with `outcome === "executed"`. This is the signal
      other panels use to re-read the watchlist after the assistant changes it.

    Mount effect: a self-contained async IIFE with a `cancelled` flag and cleanup, exactly
    as `portfolioStore.tsx` does (not a call to an exported callback — eslint-plugin-react-hooks
    7.1.1's set-state-in-effect rule was the reason for that shape, per STATE.md). Call
    `fetchChatHistory()`, set `messages` to the returned array on success, and on failure
    set `hydrateError` to the literal copy `Failed to load conversation history.` while
    setting `messages` to `[]` so the panel becomes usable rather than stuck loading.

    `sendMessage(text)`: guard re-entry with a `useRef` in-flight flag and return false
    immediately if one is already in flight (mirroring `portfolioStore.tsx`'s
    `isRefreshingRef` and `TradeBar`'s `isSubmitting` guard — this is also what prevents a
    double-submit from producing two concurrent POSTs). Then:
    1. Optimistically append a user `ChatMessage` with a client-generated id
       (`crypto.randomUUID()`), the trimmed text, empty action arrays, and
       `new Date().toISOString()`, so the user sees their own message immediately.
    2. Set `isSending` true and clear `sendError`.
    3. `await postChatMessage({ message: trimmed })`.
    4. On success: append an assistant `ChatMessage` built from the response's `message`,
       `trades`, and `watchlist_changes`. If any trade has `outcome === "executed"`, call
       `usePortfolio().refresh()` so the header total value, cash balance, and positions
       table update without a reload. If any watchlist change has
       `outcome === "executed"`, increment `watchlistRevision`. Return true.
    5. On failure: set `sendError` to the caught `Error.message` when present, otherwise
       the literal copy `Message failed to send. Check your connection and try again.`;
       roll the optimistic user message back out of `messages` by its client-generated id;
       return false. Rolling back is what lets the input keep the typed text without a
       retry duplicating the bubble.
    6. Always clear `isSending` and the in-flight ref in a `finally`.
