<objective>
Close G-04-4: the Portfolio Value chart reads as bold and busy because nothing in the four-layer
path — SQL, route, store, component — bounds the series. All ~2094 accumulated snapshots (five
days, growing) are drawn into a plot area about 126px tall by 190-430px wide: 5-11 points per
horizontal pixel, a sub-pixel x-step, and a 2px stroke that merges into an ink band four to five
times its nominal weight. A second, compounding defect: the X axis is categorical, so 17 session
gaps collapse to even index spacing and the last hour — the thing UAT Test 4 asks the user to
look at — occupies about 0.3% of the width.

Purpose: the user guessed the line was too bold. It is not. `MainChart.tsx` is the control: the
same stroke constant, the same axes, tooltip, end label and animation setting, capped at 500
points in a larger panel, and nobody complained about it. The variable that differs is density,
by a factor of ten to twenty-four. This plan fixes the variable that actually differs and leaves
the stroke exactly where the UI-SPEC put it.

Output: a bounded most-recent window enforced in SQL and exposed as a validated route parameter
with real pytest coverage; a frontend display bound that mirrors the existing
`PRICE_HISTORY_LIMIT` precedent; and an X axis that places points by elapsed time so the gaps in
the record are honest.
</objective>

<planner_assumptions>
1. **The bound is a server-side window, not a client-side trim or a downsample.** All three would
   reduce the drawn point count. A window is the smallest of the three and the only one that also
   stops the response body growing without limit, which the never-pruned table otherwise
   guarantees — so it closes `T-04-12` at the same time. A downsample (LTTB or similar) would keep
   the full time span at the cost of a new algorithm in a component with no test coverage; a
   client-side trim would leave the wire payload unbounded and would have to live in a store whose
   own gate forbids slicing. Recorded so the choice is visible rather than assumed.
2. **180 points is derived, not picked.** The debug session measured this plot at roughly 190-430px
   wide and established `MainChart.tsx` as a control that reads cleanly at about 0.46 points per
   horizontal pixel. 180 points across that width is 0.42-0.94 — the same regime, against the
   5-11 that produced the complaint. At the backend's 30-second cadence it is about the last ninety
   minutes, which is the span UAT Test 4 actually asks the user to observe.

   time, so what the panel is showing is legible from the chart itself. Adding a "last 90 minutes"

   carries.
