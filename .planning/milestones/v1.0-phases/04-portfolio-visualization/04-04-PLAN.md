backend has been recording since Phase 1, refreshed on the same 30-second rhythm it writes
them.

snapshot table and its endpoint already exist and are untouched by this phase — all that is
missing is a client that reads them. Completing this panel also completes the centre-column
layout the UI-SPEC specified.

Output: `PortfolioHistoryResponse`/`SnapshotResponse` types, `fetchPortfolioHistory()`,
`portfolioHistoryStore.tsx` and its provider, `PnlHistoryChart.tsx`, and the finished
side-by-side panel row.

<planner_assumptions>
1. **`portfolioHistoryStore` is a provider mounted in `layout.tsx`, not a bare hook (planner
   decision).** RESEARCH.md and PATTERNS.md both point at `portfolioStore.tsx` as the model,
   and that is a provider. The load-bearing reason to keep it one: a provider guarantees
   exactly one 30-second poll no matter how many components later read history, whereas a hook
   called from two components would quietly double the request rate.
2. **30-second polling is the UI-SPEC's recorded assumption, carried forward unchanged.** It
   matches the backend's own snapshot cadence, so a faster poll would mostly re-fetch identical
   rows. The UI-SPEC itself flags this as "confirm during implementation/UAT if a tighter
   post-trade refresh is wanted instead" — the natural alternative, refreshing history after
   each trade the way `portfolioStore` already does, is a small additive change if UAT asks for
   it.
3. **Zero and one snapshot share one message, deliberately.** The UI-SPEC assigns both counts
   the same copy. A single recorded point could technically render as a lone dot, but a dot
   alone in a panel reads as a broken chart rather than as an honest "nothing has happened
   yet".
4. **Unbounded history fetch is accepted, not solved (T-04-12).** The endpoint returns every
   snapshot ever recorded and this client asks for all of them every 30 seconds. That follows
   root PLAN.md §7's explicit acceptance of unbounded `portfolio_snapshots` growth at demo
   scale. Recorded in the threat register so it is findable rather than forgotten.
5. **Flagged edge-probe assumption (UI-05, `unclassified`).** The deterministic edge probe
   returned UI-05 as `unclassified` / unresolved — no edge category was assigned, so no
   predicate was auto-derived. Surfacing rather than dropping it: the UI-SPEC's three P&L rows
   are lifted into `must_haves.truths` above, but the unclassified row stays unresolved. The
   likeliest unanticipated case is two snapshots carrying identical `recorded_at` values (the
   backend writes one on a 30-second timer and one immediately after each trade, so a trade
   landing on the timer boundary can collide). Current behaviour is that both points render in
   array order at the same x position; nothing specifies whether they should be merged.
</planner_assumptions>
