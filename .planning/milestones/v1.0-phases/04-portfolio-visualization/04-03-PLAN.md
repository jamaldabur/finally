<objective>
Give the portfolio a shape. One treemap where every holding's rectangle is as big as its
weight and as green or red as its gain or loss — capped so a 40% winner cannot shout over a
10% one — plus the legend that makes that scale legible.

Purpose: UI-04 is the phase's risk-concentration surface. The positions table already lists
the same numbers; what it cannot show is that two thirds of the portfolio is one ticker, or
that the biggest tile is the reddest one. The treemap is the only view in the app where
composition and P&L are visible in the same glance.

Output: the diverging-fill helpers in `chartTheme.ts`, `PortfolioHeatmap.tsx` with its
legend and its four states, and the side-by-side panel row in `page.tsx`.
</objective>

<planner_assumptions>
1. **The diverging formula lives in `chartTheme.ts` as hex constants, not CSS variables
   (planner decision).** The UI-SPEC's formula interpolates between three tokens; an
   interpolation needs real channel values, and `var(--color-…)` cannot be mixed in JavaScript.
   The hex literals are the same values `globals.css` declares, and the plan requires a comment
   saying so, so a future palette change has one greppable second home rather than a silent one.
2. **Tile-fit thresholds are measured, not copied (RESEARCH.md Assumption A2).** RESEARCH.md's
   `width > 40 && height > 20` example is explicitly flagged there as illustrative. The plan
   requires the executor to pick a threshold against the real 10px/600 glyph run and record the
   chosen number in a comment for tuning at UAT.
3. **The tooltip's weight percentage is presentation, not derivation.** It is each tile's
   `market_value` as a share of the sum of `market_value` — a ratio of two numbers the backend
   computed, not a new financial figure, and it appears nowhere in the API contract. If UAT
   decides the weight belongs in the API, that is a Phase 5+ backend change, not a defect here.
4. **Flagged edge-probe assumption (UI-04, `unclassified`).** The deterministic edge probe
   returned UI-04 as `unclassified` / unresolved — no edge category was assigned, so no
   predicate was auto-derived. Surfacing rather than dropping it: the UI-SPEC's own UI
   Considerations table resolves eight heatmap cases and all eight are lifted into
   `must_haves.truths` above, but the unclassified row stays unresolved. The likeliest
   unanticipated case is a position whose ticker was removed from the watchlist, which the
   backend prices at cost with `pct_change` exactly `0.0` — it will render as a fully neutral
   tile that is indistinguishable from a genuinely flat position. UAT should decide whether
   that needs its own treatment.
</planner_assumptions>
