# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

No CONTEXT.md and no RESEARCH.md exist for this phase (user opted to skip discuss-phase and
research). Every open question below — charting library, treemap approach, click/selection
mechanics, empty/loading states, layout placement — was resolved here rather than asked, per
Auto Mode: each call is documented with its reasoning so it is easy to overturn during
verification if wrong. Locked, non-negotiable inputs (dark theme hex values, PLAN.md §2's three
accent colors, the ±10% saturation cap, client-side sparkline accumulation since page load) are
carried through unchanged from root `PLAN.md` §2/§6/§10 and are not re-litigated.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled Tailwind v4 components (Phase 2/3 convention, continued unchanged) |
| Charting library | **Recharts 3.x** (`npm install recharts`, verified against this repo's React 19.3.0 — `peerDependencies.react` includes `^19.0.0`) — new this phase; see "Charting library choice" below |
| Icon library | none — plain Unicode glyphs only, per Phase 3's locked convention. This phase introduces no new icons or glyphs; charts use native SVG shapes (lines, dots, treemap rects) drawn by Recharts, not an icon set |
| Font | Unchanged: system sans-serif stack for prose/labels, `--font-numeric` monospace stack (paired with `tabular-nums`) for any numeric axis tick or end-label text |

**Charting library choice.** Root `PLAN.md` §10 states a canvas-based library is "preferred (Lightweight
Charts or Recharts) for performance," naming Recharts as an explicitly sanctioned option. This phase
needs four chart-shaped surfaces: a per-row sparkline, a larger single-ticker line chart, a P&L line
chart, and a **treemap** (UI-04's heatmap). Lightweight Charts (TradingView) has no treemap primitive at
all — building the heatmap would require a second library regardless of which line-chart engine is
picked. Recharts ships `LineChart` and `Treemap` from the same package, is React-idiomatic
(declarative JSX, not an imperative canvas handle to manage across renders), and its SVG rendering is
adequate at this project's scale (single user, ≤10 watchlist tickers, ~2 ticks/second). One dependency
covers all four surfaces instead of two. This is a genuine new-dependency decision for the plan/executor
to carry forward, not a re-statement of something already locked upstream.

**No shadcn this phase**, for the same reason Phase 3 gave: Phase 2/3 already ship a complete
hand-rolled Tailwind v4 component set with no component library underneath, and introducing shadcn for
four chart wrappers would fork the visual system rather than extend it. Component Inventory and
Registry Safety sections are omitted below per template instructions for `Tool: none` projects.

## Spacing Scale

Declared values (must be multiples of 4) — inherited verbatim from Phase 2/3, unchanged:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/glyph gaps, tile-internal padding |
| sm | 8px | Compact element spacing, row gaps, treemap tile internal padding |
| md | 16px | Panel padding (`p-4`), inter-panel gaps within a column (`gap-4`) |
| lg | 24px | Top-level column gaps (`gap-6`, unchanged from Phase 2's `page.tsx`) |
| xl | 32px | Not used net-new this phase |
| 2xl | 48px | Not used net-new this phase |
| 3xl | 64px | Not used net-new this phase |

Exceptions:
- **Treemap tile gap.** A **2px** gap in the panel surface color (`--color-terminal-panel`) separates
  every adjoining tile — the dataviz mark-spec's "surface gap" principle applied to treemap cells. This
  is deliberately smaller than the 4px `xs` token because it is a data-separator, not a layout gap; do
  not round it up to 4px.
- **Chart end-marker ring.** The 2px surface-color ring around each line's end-dot (see Color) is the
  same non-scale exception, for the same reason — a rendering detail of the marker, not a spacing token.

## Typography

Inherited verbatim from Phase 3 — no new role is needed this phase, and the four base roles plus
Micro/Badge cover every text surface a chart introduces:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 12px | 400 (regular) | 1.4 |
| Heading | 14px | 500 (medium) | 1.3 |
| Display | n/a — not used this phase | n/a | n/a |
| Micro / Badge | 10px | 600 (semibold) | 1.2 |

**Recorded exception — 3-weight system (400/500/600), not 2.** This table uses three font weights
(400 regular, 500 medium, 600 semibold), which exceeds the design-contract dimension's 2-weight-max
guideline. This is a deliberate, confirmed inheritance, not an oversight: this phase reuses Phase 3's
already-shipped, already-approved 400/500/600 typography scale verbatim (see Phase 3's UI-SPEC.md line
63, and live usage across `Header.tsx`, `WatchlistPanel.tsx`, `TradeBar.tsx`, `PositionsTable.tsx`,
`PositionsRow.tsx`, `ChatPanel.tsx`, `ActionBadge.tsx`, and `WatchlistRow.tsx`). This phase introduces
no new weight and does not widen the scale further — it only extends the existing three roles to new
chart surfaces. The user confirmed this resolution on 2026-09-21, after reviewing two alternatives (a
cosmetic spec-only fix that would misrepresent already-shipped code, and a project-wide reduction to 2
weights across Phases 2-4), and chose to keep the 3-weight system unchanged rather than touch Phase 2/3
shipped code or specs.

Usage this phase:
- **Heading** (14/500/1.3): "Chart" / selected-ticker-symbol panel title, "Portfolio Heatmap" panel
  title, "Portfolio Value" panel title — identical markup pattern to the existing `<h2>Watchlist</h2>` /
  `<h2>Positions</h2>` headers (`text-sm font-medium text-terminal-text-muted`)
- **Label** (12/400/1.4): chart axis tick text (both axes, all three line charts), hover-tooltip body
  text, heatmap legend scale labels (`−10%` / `0%` / `+10%`)
- **Micro/Badge** (10/600/1.2): treemap tile ticker symbol and pct_change text (tiles are small — this
  matches the existing precedent of 10px/600 being this app's compact-label size, e.g. the header's
  "Simulated" badge)
- **Body** (14/400/1.5): all new empty/loading/error state copy (matches existing
  `text-sm text-terminal-text-muted` / `text-sm text-red-400` panel-message convention verbatim)

**Numeric text rule (carried from Phase 2's `tabular-nums` convention, extended):** any chart end-label
showing a price or portfolio value uses `tabular-nums` + `--font-numeric`, matching every other numeric
cell in the app (`WatchlistRow`, `PositionsRow`, `Header`). Axis tick numbers get the same treatment.

## Color

Base four roles are unchanged, global tokens carried forward:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0d1117` (`--color-terminal-bg`) | Page background |
| Secondary (30%) | `#1a1a2e` (`--color-terminal-panel`) | Chart/heatmap panel surfaces |
| Accent (10%) | `#ecad0a` (`--color-accent-yellow`) | Unchanged this phase — brand wordmark, "Simulated" badge, chat unread dot only. **No new yellow usage is introduced by this phase.** |
| Destructive | `#f87171` (`--color-loss`, literal `text-red-400` in code) | Error-state copy across all four new panels (reused, unchanged meaning) |

Additional semantic rows this phase needs:

| Role | Value | Usage |
|------|-------|-------|
| Gain | `#4ade80` (`--color-gain`, literal `text-green-400`/`bg-green-500` in code) | Sparkline/main-chart/P&L-chart line + end-dot color when the tracked series is trending up since its reference point; positive arm of the heatmap's diverging fill |
| Loss | `#f87171` (`--color-loss`) | Same three charts' line/dot color when trending down; negative arm of the heatmap's diverging fill |
| Neutral midpoint (new use) | `#30363d` (`--color-terminal-border`) | Heatmap fill at pct_change = 0% (the diverging scale's gray midpoint); doubles as every chart's gridline/axis-line color (already this app's "one-step-off-surface" muted tone) |

**Accent reserved for** (extends, never loosens, Phase 3's list): Yellow/Purple/Blue rows are
**unchanged and untouched by this phase** — no chart introduces a new yellow, purple, or blue usage.
Gain/Loss are reused exactly as their existing meaning (price-up/price-down, P&L sign), now also driving
chart line colors and the heatmap's two arms — no new hue is introduced anywhere in this phase.

**Why no accent-blue selection highlight.** A selected watchlist row (the click target for the main
chart) needs a visual "you are here" state. Phase 3 explicitly forbids extending accent-blue beyond the
assistant-chat border accent ("Do not use... any watchlist/price element — blue has no meaning there
today"). Rather than amend that reservation, the selected row uses a **neutral** highlight:
`bg-terminal-border/50` background tint, no accent hue spent. Unselected-row hover uses the same token
at lower opacity: `hover:bg-terminal-border/20`.

### Heatmap diverging fill — exact formula

Per the dataviz skill's diverging-color job (two hues + neutral midpoint, equal steps per arm) and this
phase's own ±10% saturation cap (root `PLAN.md` §10):

```
intensity = min(abs(pct_change), 10) / 10        // clamps to [0, 1]; pct_change in percent, e.g. 7.5
fill = pct_change >= 0
  ? mix(#30363d, #4ade80, intensity)              // neutral -> gain
  : mix(#30363d, #f87171, intensity)              // neutral -> loss
tile_text_color = intensity >= 0.5 ? #0d1117 : #e6edf3   // dark ink on saturated fills, light ink on pale ones
```

`mix(a, b, t)` is a standard linear interpolation between two colors by factor `t` (RGB or OKLCH — either
is acceptable; OKLCH is preferred for a perceptually even ramp but not mandatory at this two-stop scale).
This uses only tokens already in this project's palette (`--color-terminal-border`/`--color-gain`/
`--color-loss`) — no new arbitrary hex is introduced, satisfying the dataviz skill's "documented palette
only" check. The categorical CVD validator does **not** apply here (it validates identity/categorical
palettes; a two-hue diverging ramp is out of its scope by design, per the skill's own scope note) — the
only per-tile obligation is the `tile_text_color` contrast switch above, which keeps label text readable
against every fill the formula can produce.

### Line/marker mark spec (all three line charts: sparkline, main chart, P&L chart)

| Element | Spec |
|---|---|
| Line | 2px stroke, round join/cap, color = gain or loss per the trend rule below |
| End-of-line marker | Filled dot, ≥8px diameter (r≥4), same color as the line, with a 2px ring in the immediate surface color (`--color-terminal-panel` for main/P&L charts, `--color-terminal-panel` for the sparkline too since it sits inside `WatchlistPanel`) |
| End-label text (main chart + P&L chart only — **not** the sparkline) | `tabular-nums`, `--font-numeric`, colored `--color-terminal-text` — **never the line's gain/loss color** (dataviz rule: "text never wears the data color"; identity comes from the adjacent colored dot, not colored text) |
| Gridlines / axes | `--color-terminal-border`, hairline 1px, solid (never dashed) |
| Axis tick text | Label role, `--color-terminal-text-muted` |
| Area fill (optional polish, executor's call) | If added under the main/P&L chart line, the line's own color at ~10% opacity — a wash, never a saturated block |

**Trend/color rule (single source of truth, reused across all three charts):** a series is "up" — and
therefore rendered in gain color — when its latest accumulated value is ≥ its first recorded value since
the relevant reference point (page load for tickers, first loaded snapshot for the P&L chart); otherwise
it renders in loss color. For per-ticker charts (sparkline, main chart) this reuses `priceStore`'s
existing `firstPrices` map verbatim — the exact same value already driving `WatchlistRow`'s green/red
change% text — so a ticker's sparkline, its main-chart line, and its watchlist % figure can never
disagree on trend direction. The P&L chart applies the identical rule to
`portfolio_snapshots` (first loaded snapshot vs. latest).

No legend box is needed on any of the three line charts — each is a single series, and its panel title
(or the selected ticker symbol) already states what is plotted, per the dataviz skill's single-series
rule.

## UI Considerations

Ran the deterministic `ui-consideration-probe` engine over 6 described surfaces (sparkline, main chart
panel, portfolio heatmap, heatmap tile label, P&L history chart, watchlist row click) — 25 applicable
(element × category) combinations. Every applicable combination is resolved: 17 explicit, 0 backstop, 8
dismissed as not-applicable (reason given per row — dismissal is a recorded resolution, never a silent
drop). 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Sparkline, before any SSE tick since page load | ✅ resolved (explicit) | Renders a flat muted baseline (no data points) rather than a blank gap or spinner — matches UI-02's "filling in progressively" language |
| loading | Sparkline | dismissed — N/A | No distinct async loading phase — data arrives incrementally over the shared SSE connection; the empty-state row above covers the 0-tick case, and each subsequent real change simply extends the line |
| error | Sparkline | dismissed — N/A | No fetch of its own to fail; a lost SSE connection is already surfaced globally by the header's connection dot (Phase 2) — the sparkline just stops extending |
| populated | Sparkline, exactly 1 recorded point | ✅ resolved (explicit) | Renders as a flat line / lone dot at that price, not an error or blank chart — the next real change begins the visible trend |
| populated | Sparkline, 2+ recorded points | ✅ resolved (explicit) | Normal progressively-extending 2px line + end-dot, colored per the Trend/color rule |
| empty | Main chart panel, no ticker selected | ✅ resolved (explicit) | Renders the "No ticker selected" heading + body (Copywriting Contract) |
| loading | Main chart panel, ticker selected but <2 points accumulated | ✅ resolved (explicit) | "Waiting for price data…" — distinct from the no-selection empty state because a ticker IS chosen |
| error | Main chart panel, SSE disconnected mid-view | dismissed — N/A | No separate in-chart error UI; the header connection dot already reports this globally, and the chart holds its last known line (same reasoning as the sparkline's error dismissal) |
| populated | Main chart panel, 2+ points | ✅ resolved (explicit) | Full line chart: axis ticks, hover crosshair+tooltip, end-dot + end-label showing the latest price |
| empty | Portfolio Heatmap, 0 positions | ✅ resolved (explicit) | Renders the heatmap empty-state copy (Copywriting Contract) instead of a blank panel |
| loading | Portfolio Heatmap, initial `GET /api/portfolio` in flight | ✅ resolved (explicit) | "Loading portfolio…" — reuses `usePortfolio()`'s existing `loading` flag, no new fetch |
| error | Portfolio Heatmap, portfolio fetch failed | ✅ resolved (explicit) | `text-sm text-red-400 role="alert"`, same pattern as `PositionsTable`'s existing error row (same `usePortfolio()` error state, no new error path) |
| populated | Portfolio Heatmap, typical position count | ✅ resolved (explicit) | Treemap tiles sized by `market_value` weight, filled per the diverging formula above |
| partial | Portfolio Heatmap | dismissed — N/A | `compute_portfolio_view()` is the sole backend authority and always returns complete `PositionView` rows (root D-04) — no partially-populated position shape can reach the frontend |
| overflow | Portfolio Heatmap tile, weight too small for its label to fit | ✅ resolved (explicit) | The pct_change label drops first; if the ticker symbol still doesn't fit, the tile shows no inline text at all and relies on its hover tooltip (ticker, weight%, pct_change) — text is never clipped |
| zero-one-many | Portfolio Heatmap, exactly 1 position | ✅ resolved (explicit) | Renders as one full-panel tile — Recharts' `Treemap` handles a single-node dataset without special-casing |
| zero-one-many | Portfolio Heatmap, many positions | ✅ resolved (explicit) | Same tiled layout scales to the watchlist's ticker ceiling (10 in the default seed); no pagination needed at this project's scale |
| long-text | Heatmap tile ticker label | dismissed — N/A | Tickers are validated against the simulator's fixed universe (root `PLAN.md` §6) — always 1-5 uppercase characters, no long-text risk |
| empty | P&L History chart, 0 or 1 snapshot | ✅ resolved (explicit) | Renders "Not enough history yet…" (Copywriting Contract) — a line needs 2+ points; both counts share this copy |
| loading | P&L History chart, `GET /api/portfolio/history` in flight | ✅ resolved (explicit) | "Loading portfolio history…" |
| error | P&L History chart, history fetch failed | ✅ resolved (explicit) | `text-sm text-red-400 role="alert"`, same pattern as the other three panels |
| populated | P&L History chart, 2+ snapshots | ✅ resolved (explicit) | Line chart colored by overall trend, end-dot + end-label showing the latest `total_value`, hover tooltip with timestamp |
| loading | Watchlist row click (ticker selection) | dismissed — N/A | Selecting a ticker is a synchronous client-side state update — nothing is fetched, so nothing loads |
| error | Watchlist row click | dismissed — N/A | Same reason — no async operation, nothing that can fail |
| long-text | Watchlist row click target | dismissed — N/A | This phase only adds a click handler and hover/selected styling to the existing Phase 2 row — no new text content is introduced |

**Assumption (P&L chart poll cadence):** The P&L chart polls `GET /api/portfolio/history` on its own
30-second interval (matching the backend's own snapshot-recording cadence, root PLAN.md §7), independent
of `portfolioStore`'s 5-second refresh. Not explicitly required by any upstream artifact — a reasonable,
low-complexity default; confirm during implementation/UAT if a tighter post-trade refresh is wanted
instead.

**Assumption (price-history buffer cap):** Each ticker's client-accumulated price-history array (backing
both the sparkline and the main chart) is capped at 500 points, FIFO-dropping the oldest on overflow.
This is a new frontend-only memory bound, distinct from and not in conflict with `portfolio_snapshots`'
already-accepted unbounded backend growth (root PLAN.md §7) — that table's unboundedness is an accepted
tradeoff for a different, persisted dataset; this array is ephemeral, in-memory, and rebuilds on every
page load, so bounding it costs nothing a user would notice at demo scale.

## Layout & Interaction Contract

*(Not a template section, but load-bearing for this phase — the executor needs the concrete data-flow
and placement decisions the open questions above resolved.)*

**New client-side state.**
1. **Price-history store** (extends `priceStore.tsx` or a new sibling context — executor's call which,
   as long as it stays inside the existing `PriceStoreProvider` tree so it sees every tick): a
   `Map<string, {timestamp: string, price: number}[]>`, one entry per ticker, appended to **only when
   the incoming tick's price differs from that ticker's last recorded point** — the same "real change"
   semantics `PriceCell` already uses for its flash trigger, not `previous_price`. Capped per the
   500-point Assumption above. Both `Sparkline` and `MainChart` read from this single buffer (DRY — no
   second accumulation loop).
2. **Selected-ticker state**: a single `string | null`, lifted into `page.tsx` (or a small new
   `ChartSelectionProvider` if the executor prefers a context — two consumers, `WatchlistRow` as writer
   and the main chart panel as reader, is small enough for either approach). `null` on first load (no
   default ticker pre-selected) — the empty state is the deliberate first-launch appearance, matching
   this phase's "select to drill in" framing.
3. **Portfolio-history fetch**: a new `fetchPortfolioHistory()` in `lib/api.ts` (`GET
   /api/portfolio/history`, following the existing `fetchPortfolio()`/`fetchWatchlist()` pattern exactly
   — same error-passthrough convention), consumed by a new small store/hook polling every 30s per the
   Assumption above.

**Watchlist row changes** (`WatchlistRow.tsx`, extends the existing Phase 2 component):
- Add a `Sparkline` mini-chart between the ticker symbol and the price/change% block:
  `flex-1 min-w-0`, fixed height `h-5` (20px, matching the row's compact `py-1.5` rhythm), no axes, no
  tooltip, no legend — line + end-dot only, per the mark spec above.
- The whole row becomes a click target (`onClick`, `cursor-pointer`, `role="button"`) that sets the
  selected-ticker state to `entry.ticker`. Selected state: `bg-terminal-border/50`. Hover (unselected):
  `hover:bg-terminal-border/20`. Neither state spends an accent hue (see Color, "Why no accent-blue
  selection highlight").

**Center-column layout** (`page.tsx`'s `<main>`, currently a single bordered panel wrapping only
`PositionsTable`): restructured into an unstyled `flex flex-col gap-4` container (matching the left
column's existing `gap-4` convention) holding four sibling panels, each independently carrying the
established panel shell `rounded-lg border border-terminal-border bg-terminal-panel p-4`:

1. **Main Chart panel** (top, full width, `h-72` / 288px chart area) — `MainChart` component, heading +
   states per Copywriting/UI-Considerations above. Placed first because it is this phase's primary
   drill-down surface, directly reachable from the watchlist click just to its left.
2. **A `flex gap-4` row** holding two equal-width (`flex-1`) panels side by side, each `h-60` / 240px:
   - **Portfolio Heatmap panel** (left) — `PortfolioHeatmap` component (Recharts `Treemap`), plus the
     small diverging-scale legend strip (a ~120px-wide, 6-8px-tall horizontal gradient bar running
     loss→neutral→gain, with the "−10%"/"0%"/"+10%" Label-role text beneath it) positioned in the
     panel's header row, right-aligned opposite the "Portfolio Heatmap" title.
   - **Portfolio Value panel** (right) — `PnlHistoryChart` component (P&L line chart), heading "Portfolio
     Value".
3. **Positions Table panel** (bottom, full width) — the existing `PositionsTable` component, now wrapped
   in its own bordered panel shell for visual consistency with the three new panels above it (it
   previously inherited the border from `<main>` directly; no change to `PositionsTable.tsx` itself is
   needed, only to what wraps it in `page.tsx`).

This keeps the three-column shell (`Header` full-width, then `Watchlist+TradeBar` | center | `ChatPanel`)
entirely intact — only the center column's internal structure changes. The center column may now exceed
one viewport's height at typical window sizes; this is an accepted desktop-first tradeoff (root PLAN.md
§2, "responsive but desktop-first... functional on tablet") — the column scrolls with the page, nothing
is clipped or hidden.

**Hover/tooltip behavior:** Main chart and P&L chart both ship a crosshair + tooltip on hover (dataviz
skill: "ship a crosshair+tooltip on line/area, by default"), styled `bg-terminal-panel
border border-terminal-border rounded text-terminal-text` (Label role body), showing the hovered point's
formatted timestamp and price/value. Heatmap tiles get a per-tile hover tooltip (ticker, weight %,
pct_change) using the same styling — this is also the fallback the overflow row above relies on when a
tile is too small for inline text. The sparkline gets **no** tooltip — it is too small (20px tall, inline
in a dense row) for a meaningful hit target, and the row's existing `PriceCell` already shows the exact
current price beside it; this is a deliberate, explicit dismissal, not an oversight.
