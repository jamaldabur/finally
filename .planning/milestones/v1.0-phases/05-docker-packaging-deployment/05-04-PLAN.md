<objective>
**As a** user of FinAlly, **I want to** start the entire application with a single command and have
my data persist across restarts, **so that** I get the one-command trading terminal Phase 5
promises. On Windows, that also means a mistyped flag, or the bash launcher's `--build` typed out
of habit, is refused on the spot and is never silently ignored or silently turned into a rebuild
and restart that I did not ask for.

This is a gap-closure plan (Wave 4) with one gap and one review correction. 05-VERIFICATION.md
scored 13/14. The failed truth is that `scripts/start_windows.ps1` does not reject an unrecognised
argument. The verifier reproduced it three times against the committed script:
`--build`, `--totally-bogus-flag` and `--i-am-not-a-real-flag` all exited 0 with no usage message,
and `--build` triggered a real rebuild and container replacement. That falsifies 05-02-PLAN.md's
must-have and prohibition and its T-05-08 mitigation claim. It also shows that 05-REVIEW.md's WR-04
predicted the wrong symptom (a ParameterBindingException dump).

**Plan-time grounding.** All of this was done in the session scratchpad and in temp copies. Nothing
in the repository was modified.

The root cause was established by probe, not by assumption:
- The script has no cmdlet-binding attribute, so it is not an advanced script. For that kind of
  script PowerShell never raises a binding error for an unbound token. The token is collected
  into the automatic `$args` variable and ignored.
- Under `powershell -File`, powershell.exe's own command-line parser also rewrites `--build` and
  `--Build` into the `-Build` switch. They then arrive as `$Build = True` with `$args` empty, so no
  check on `$args` can tell them apart from `-Build`.
- Under in-session invocation (`& .\scripts\start_windows.ps1 --build`) the same token instead lands
  in `$args` and the switch stays False. A declared switch parameter therefore validates nothing in
  either mode, and it behaves differently between the two.
- `scripts/stop_windows.ps1`'s empty `param()` has the same property. A temp copy run with
  `--totally-bogus-flag`, `-Force` or `extra` printed "FinAlly is not running." with rc=0 after
  querying Docker. With the app up, the same invocation would stop it.
- Adding a cmdlet-binding attribute is not a fix. Unknown tokens then print the raw error-record
  block (the WR-03 failure mode), `--build` is still silently accepted under `-File`, and `-Verbose`
  binds silently.
- A prototype with an empty `param()` and an exact-match check on `$args` gave identical results
  under `-File` and in-session:
  - Accepted, reaching step 2: no argument, `-Build`, `-build`, `-BUILD`.
  - Rejected with the usage line and rc=1: `--build`, `--Build`, both bogus flags, `-Buld`, `-B`,
    `foo`, an empty-string argument, `-Build extra`, and `-Verbose`.

The docker-free verify commands in Tasks 1 and 2 were dry-run against the unfixed scripts. They
print the RED baseline (usage=0, env_guard=1 for the launcher; reached_docker=1 for the stopper),
so they cannot pass vacuously.

**Plan-time decision P-03: the double-dash spelling is rejected on Windows.** This resolves a
conflict in the source artifacts:
- VERIFICATION.md's concrete re-test list says `--build` must exit 1 and that a bare invocation
  and `-Build` stay unchanged. The orchestrator restated this.
- VERIFICATION.md's looser allowed-set phrase and the orchestrator's re-test note also list
  `--Build` as accepted.

PowerShell users treat `--build` and `--Build` as the same token, and only a case-sensitive split
could satisfy both statements, which would be an incoherent UX. This plan follows the concrete
re-test list: the Windows launcher accepts `-Build` in any letter case and rejects both double-dash
spellings.

D-06 is honoured unchanged. Its substance is "build only when missing or when explicitly forced".
Plan 05-02 established `-Build` as the PowerShell spelling of that flag (its Artifacts list: CLI
switch parameter `-Build` on `scripts/start_windows.ps1`) and proved it live. `--build` remains the
bash launcher's spelling. No README or PLAN.md text documents `--build` for Windows. Admitting it
later as an explicit, documented alias would be a one-line change.

Purpose: close the only failed Phase 5 must-have with evidence that exercises the real script in
both invocation modes and against the live daemon, apply the identical fix to the stop script
under the same 05-02 truth, and correct the review record so no later fix targets the symptom
WR-04 predicted.

Output:
- An explicit step-1 guard in `scripts/start_windows.ps1` and in `scripts/stop_windows.ps1`.
- A correction appended to WR-04 in `05-REVIEW.md`.

Task 1 is the tracer. It covers the gap end to end: from the command line, through the script's
new first step, to the daemon, which must be left untouched on rejection. Task 2 is the same slice
on the stop side. Task 3 fixes the record.
