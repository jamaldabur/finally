## Phase Goal

**As a** developer maintaining FinAlly, **I want to** run backend, frontend and end-to-end suites
that exercise the whole trading loop, **so that** I can change any layer and know within minutes
whether watch, trade, chat and portfolio still work together.

This plan is the tracer for the end-to-end third of that story (TEST-05). Nothing E2E exists today —
`test/` holds only a stray, partial, untracked `node_modules`. This plan builds the harness PLAN.md
section 12 specifies — a separate `test/docker-compose.test.yml` running the real app image plus a

then adds the portable one-command runner and the SSE reconnection scenario. Plan 06-06 adds the
trading-loop specs on top.

Purpose: an E2E suite is only trustworthy if every run starts from the same seeded database, never
touches the user's data or their running app, and never calls a real LLM. Those properties are
built in here, before any trading spec depends on them.

Output: a committed `test/` project, a green `npm --prefix test run e2e`, and two specs.

<planner_decisions>
- **P-08 — a dedicated runner image, not a bind-mounted host install.** RESEARCH.md Pattern 3 bind-
  mounts `test/` into the stock Playwright image and runs `npx playwright test`, which would execute
  against a host `node_modules` installed on Windows (or none at all). Instead `test/Dockerfile.playwright`
  starts from the pinned Playwright image and runs `npm ci` against the committed lockfile, so the
  runner is hermetic and identical on every host.
- **P-09 — build context `..`.** The compose file lives in `test/`, so the repo root is `..`.
  RESEARCH.md Pattern 3's `../..` points one level above the repository and would fail to find the
  Dockerfile.
- **P-10 — serial, ordered, no retries.** All specs share one single-user database. Specs run with
  one worker in file-name order (`01-` ... `06-`), with `retries: 0`. Only `01-fresh-start` asserts
  absolute seed values; every later spec measures its own before/after deltas.
- **P-11 — `$10000.00`, not `10,000`.** The header formats with `formatCurrency` (`$` plus
  `toFixed(2)`, no thousands separator). RESEARCH.md's skeleton regex `/10,000/` would never match.
- **P-12 — `shm_size` instead of a shared host IPC namespace.** Chromium needs more shared memory
  than Docker's 64 MB default; a 1 GB `shm_size` provides it without joining the host's IPC
  namespace.
- **P-13 — reconnection proven two ways.** A live drop via `context.setOffline()` exercises the
  in-flight stream failing and recovering; an unreachable-at-load stream via `page.route` aborting
  with the `internetdisconnected` error code proves the browser's own retry loop. The error code
  matters: an `aborted` code is treated by Chromium as a cancellation, after which EventSource gives
  up instead of retrying.
- **P-15 — reuse the image HEALTHCHECK unchanged (D-08).** The compose file declares no
  healthcheck override. The image probes every 30s, so the runner starts roughly 30s after the app —
  an accepted cost for having exactly one health-check definition.
- **P-16 — the runner is a Node script.** Pre-clean and always-teardown need "run the next command
  regardless of the previous exit code", which has no portable npm-script spelling across cmd.exe
  and POSIX shells. `test/run-e2e.mjs` uses `child_process.spawnSync` and works the same on Windows,
  macOS and Linux.
- **P-07 — no test ids.** Specs locate elements by role, label and visible text only. Adding test ids
  would change frontend UI source, which the phase boundary forbids (closes RESEARCH Open Question 1).
</planner_decisions>

| E2E harness -> user's data | The app under test writes a real SQLite database; the harness must never point it at the user's `db/` or production volume |
