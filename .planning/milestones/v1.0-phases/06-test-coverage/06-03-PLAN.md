<objective>
## Phase Goal

**As a** developer maintaining FinAlly, **I want to** run backend, frontend and end-to-end suites
that exercise the whole trading loop, **so that** I can change any layer and know within minutes
whether watch, trade, chat and portfolio still work together.

This plan covers two of TEST-04's four frontend areas: **watchlist CRUD** and **chat rendering /
loading state**. It uses the harness from 06-02 (`stubFetch`, `deferred`, `renderWithProviders`,
`StubEventSource`) and adds no infrastructure of its own.

**P-06 — what "watchlist CRUD" means in this frontend.** The frontend has no manual add/remove
control: `frontend/lib/api.ts` exposes no watchlist mutation and `WatchlistPanel.tsx` renders no
input. Watchlist changes reach the UI only through the chat copilot: an executed change bumps
`watchlistRevision` in `chatStore.tsx`, which is a dependency of `WatchlistPanel`'s fetch effect.
So this plan tests the frontend's actual CRUD surface — read (loading, rows, live price, empty,
error) and chat-driven create and delete, plus the rule that a rejected change does not re-fetch.
Adding a manual control would be a UI change, which the phase boundary forbids.

Purpose: prove the two frontend behaviors most likely to regress silently — a watchlist that stops
reflecting chat-made changes, and a chat panel whose loading, success and failure states drift.

Output: three colocated test files.
</objective>
